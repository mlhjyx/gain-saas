## 0. 一句话

**把已经存在的获客引擎装进一个可用的 SaaS 壳**:一期交付"账户与工作空间(自建)+ 卖家自助建档 + 买家知识可视化 + 发现与资格判断主线产品",终点是"用户接受一条线索、引擎产出不可变资格交付包、SaaS 完成消费回执"的第一次端到端闭环——**不含**触达发送、机会/QGO 中心与订阅计费。

## 1. 背景、目标与边界

### 1.1 背景

产品是面向中国 B2B 出口企业的海外增长机会操作系统(总设计 §1)。引擎仓 `global/backend` 已实现买家智能与机会资格引擎(采集、知识、发现、评分、资格交付包,止于 `LeadQualifiedPackage`),但没有任何用户产品:身份、组织、工作空间、界面全部缺位。gain-saas 承担 SaaS Control Plane 与全部用户交互,把这些能力变成可注册、可使用、可交付的产品。

引擎侧边界拍板(`product-scope.md` §3.2):**SaaS 拥有身份、Organization、Workspace、Membership、Billing/Credits**;引擎拥有采集、Identity/Canonical、Evidence、数据权利、Signal、Reachability 与资格输入;Qualification & Handoff 止于不可变交付包 + Outbox/ACK,**SaaS 独占服务端 consumer/receipt/snapshot 事务**。本文据此划界。

### 1.2 一期目标

| 编号 | 目标 | 可验证结果 |
| --- | --- | --- |
| G1 | 组织底座可用 | 新用户可注册、建工作空间、邀请成员并按角色操作获客功能 |
| G2 | 卖家建档闭环 | 客户能录完"核心产品 + 目标市场"并通过 completeness/confirm 形成可用档案(含人工认领兜底路径) |
| G3 | 获客可发起可观察 | 客户能从档案创建 ICP、确认查询计划、发起发现 run 并看到进度与终态(含 PARTIAL 如实展示) |
| G4 | 线索可判可交付 | 用户能对线索 accept/reject;accept 产生的 `LeadQualified` 事件被 SaaS 消费并 ACK,**端到端第一次走通**(引擎侧 279 条 PENDING 积压的现状必须因此改变) |
| G5 | 交付有节奏 | 周报可见、CSV 可导出(合规计数如实展示)、反馈可回填 |

北极星(每活跃 Workspace 每月新增 QGO)属于模块 08,后置;一期代理指标:完成 confirm 的卖家档案数、ACTIVE ICP 数、跑完(PARTIAL 及以上)的 run 数、人工裁决数、`LeadQualified` ACK 成功率、周报反馈回填数。

### 1.3 分工边界

| 职责 | 归属 | 说明 |
| --- | --- | --- |
| 注册登录、组织/工作空间、成员与角色、JWT 签发与 JWKS | **gain-saas** | 引擎零实现,只做验签与 scope 守卫 |
| 卖家档案页面与建档向导 | gain-saas | 数据落在引擎 `/companies` 族端点 |
| 买家知识持续采集、核验、整合 | 引擎 | 后台独立运行,SaaS 不参与编排 |
| 发现 run 的执行与稳定性 | 引擎 | SaaS 只发起与展示 |
| `LeadQualified` 的消费、回执、快照事务 | **gain-saas** | `product-scope.md` 明确 SaaS 独占 |
| 数据删除请求(DSR)的受理页面 | gain-saas(受理)→ 引擎(执行) | 转发 `/deletion-requests` |
| API 合同真值 | 引擎 | 以运行实例 OpenAPI 门户为准,两侧不得各自手写平行合同 |
| 平台运营台(原获客中台) | **gain-saas 运营域**(SD9) | acquisition-admin 不再独立部署;运营功能并入 gain-saas,operator 角色专用(§13) |

### 1.4 设计原则

1. **产品形态跟随引擎现实**:引擎自助入驻链路当前故障、run 尚无一次完整跑完(见 §11),一期产品流程必须为两者提供人工/半自动兜底,不把 UI 建立在"引擎必然成功"的假设上。
2. **不复制合同**:所有端点、错误码、状态枚举以引擎 OpenAPI 为唯一真值;SaaS 侧只维护"页面如何组合这些端点"。
3. **合规默认收紧**:个人数据相关 scope(`personal-data:read`)一期不授予任何 SaaS 角色;个人联系方式默认不在界面出现(引擎侧公司级联系路径是唯一可达性口径)。**例外(M4,2026-10-31 联系人挖掘设计经产品负责人批准)**:工作空间管理员可在线索档案包看到「决策人」卡片(姓名/职位/部门/联系方式的验证状态与来源证据),引擎侧以独立的窄 scope `contact-discovery:read` 控制(只授予 `saas-admin`,不覆盖事件流/线索详情/建站档案);成员仍不可见,`personal-data:read` 仍不授予任何用户角色。
4. **如实呈现**:run 的 FAILED/PARTIAL、导出的 withheld 计数、交付被拦的原因必须如实展示,不美化、不隐瞒;界面用语按 §14.2 映射为用户语言,原始错误码与 trace 保留在「技术详情」折叠区。
5. **直觉优先**:用户全程不需要理解引擎概念即可走完主链路;任何时刻界面都能回答"我在哪、下一步做什么";等待有预期、失败有出路(§14)。

## 2. 用户与角色

### 2.1 用户画像(总设计 §1)

- **决策者**(老板/出海负责人):购买与授权,关注结果与成本;一期是主要付费角色,但使用浅。
- **操作者**(海外增长/外贸运营):日常主用户;建档、建 ICP、跑发现、裁线索、发周报。

销售角色属模块 08(机会与 QGO),一期不建。另有一类**平台运营用户(自己人)**:运维数据源、调度与预算、排障跨租户问题,不使用租户业务界面,属运营域(SD9,§13)。

### 2.2 角色与权限(一期方案)

引擎侧权限 = token 内 `roles` → 引擎 scope 的映射(引擎经 `AUTH_ROLE_SCOPE_MAP_JSON` 配置)。**租户详情合同是 `LeadPackage`（`GET /leads/:id/package`）**；禁联名单仅 admin 可见（本 workspace）；`personal-data:read` 一期不授予任何 SaaS 角色（不变）；M4 的具名联系人面改用独立的窄 scope `contact-discovery:read`，只授予 `saas-admin`。一期 SaaS 建两档**租户**角色(admin/member)与一个**平台**角色(operator,不映射任何引擎业务 scope,见 SD9):

| SaaS 角色 | 映射到的引擎 scope | 可做的事 |
| --- | --- | --- |
| 管理员 `admin` | `acquisition:read` `acquisition:write` `acquisition:review` `acquisition:event:ack` `acquisition:label:write` `acquisition:identity:review` `acquisition:export` `compliance:manage` `contact-discovery:read` | 全部业务操作,含认领审批、制裁复核、删除请求、CSV 导出、决策人卡片（具名联系人） |
| 成员 `member` | `acquisition:read` `acquisition:write` `acquisition:review` `acquisition:label:write` | 建档、建 ICP、跑 run、裁线索;不含审批/制裁复核/导出/合规 |
| 平台运营 `operator`(平台角色) | 无(不调引擎业务 API) | 运营域(§13):数据源管理、调度、预算查看、跨租户只读诊断;不属于任何 workspace |

不映射到任何 SaaS **用户** 角色:`ops:read`(引擎运维)、`acquisition:identity:review` 仅 admin(认领审批是信任动作)。两个 scope 只授予**服务身份**(机器账号,不签发给任何用户 token,见 SD5):

- **事件消费服务身份**(唯一一个):持有 `acquisition:read` + `personal-data:read` + `acquisition:event:ack`。前两者是 `GET /events` 的 AND 语义硬要求(引擎守卫按"全部满足"校验,`apps/api/src/auth/scopes.guard.ts`),不是合规让步——红线是"个人数据不出现在界面、不进用户 token",服务身份两者都不违反。

**平台角色与租户角色的隔离(SD9)**:`operator` 是平台员工账号,由既有 operator 在控制台创建(第一个由部署引导创建),不走注册——注册入口只产出 admin/member。operator 登录后直接进入运营域界面,不进入任何工作空间;其会话不映射任何引擎 scope,运营域经 PostgreSQL 白名单与 Temporal 集成面操作引擎(§13),与租户域的 BFF/引擎 HTTP 面完全分开。租户 admin/member 永远看不到跨工作空间数据。

引擎可用的 scope 全集共 10 个,以 `apps/api/src/auth/scopes.ts` 为准;`AUTH_ROLE_SCOPE_MAP_JSON` 属引擎部署配置,由 SaaS 提出映射、引擎运维落配置。

### 2.3 Token 合同(SaaS → 引擎)

| 项 | 要求 |
| --- | --- |
| 形态 | JWT,RS256/ES256,JWKS 公开可取 |
| 必含 claims | `sub`(用户标识)、`workspace`(UUID,租户主键,claim 名可配置)、`roles`(字符串数组)、标准 `iss/aud/exp/iat` |
| 有效期 | 一期 ≤ 60 分钟,前端静默刷新;角色/成员变更即时生效依赖短 TTL |
| JWKS | SaaS 提供 `.well-known/jwks.json`(或 IdP 托管);换钥走双钥重叠期 |
| 验签 | 引擎 `jwks-token-verifier` 按 issuer/audience 配置校验;clock skew 缺省 60s |

## 4. 模块 01:账户与工作空间(SaaS 全自建)

### 4.1 定位

引擎没有用户、组织、成员的任何实现(引擎内 `Workspace` 仅为来自 token 的租户影子行,首次 `POST /companies` 时自动建立)。本模块是所有模块的前提,也是 SaaS Control Plane 的第一期。

### 4.2 功能需求

| 编号 | 功能 | 要求 |
| --- | --- | --- |
| A1 | 注册 | 企业邮箱 + 密码 + 公司名称;一人一个主账号;注册即创建默认工作空间 |
| A2 | 登录与会话 | 邮箱密码;会话以短 TTL JWT 表达;登出、改密 |
| A3 | 工作空间 | 名称可改;UUID 为租户主键;一个账号可属多个工作空间并支持切换(已决 SD2:membership 模型多对多,UI 只做切换器与创建/退出,不做高级管理) |
| A4 | 成员管理 | 邀请(邮件链接)、移除、角色变更(管理员/成员,§2.2);成员列表 |
| A5 | JWKS 与签发 | 按合同 §2.3 签发;暴露 JWKS;换钥流程 |
| A6 | DSR 受理 | 隐私设置页提交数据删除请求 → 转发引擎 `/deletion-requests`,展示回执状态;**删除级联到 SaaS 自有库**:SaaS 事件快照库因事件消费持有 `personal-data:read` 而属于含个人数据的库,引擎执行删除后,SaaS 侧对应 workspace/主体的快照记录一并删除并留痕(见 SD5) |
| A7 | 操作审计 | 成员/角色/邀请等控制面动作留痕(自查库,不依赖引擎) |
| A8 | 工作台与新手引导 | 登录首页:六步主链路进度条(§14.1)、"下一步"任务清单(按档案完整度/ICP/方案/待判断线索自动推导,永远给出唯一下一步)、进行中寻源与站内通知入口;首次登录以同一清单引导完成步骤 1–3(§14.3) |

### 4.3 业务规则

- 工作空间与引擎租户 1:1;**不做**工作空间删除(引擎侧擦除走 DSR/A6)。
- 角色变更不改已签发 token;靠短 TTL + 刷新收敛,不要求引擎即时失效。
- 邮箱域名不限制;一期不做 SSO/LDAP/手机号。

### 4.4 验收标准(节选,完整见 §9)

- 新注册用户 10 分钟内可完成"邀请第二个成员并使其以成员权限操作"。
- member 角色调用任何审批/导出/合规端点被引擎 403,界面有对应降级。

## 7. 模块 04:买家发现与资格判断(一期主线)

### 7.1 定位

产品主链路:卖家的产品与市场 → ICP → 查询计划(确认制)→ 发现 run → 线索队列 → 人工裁决 → 不可变资格交付包。这是客户购买的核心价值,也是一期工程重心。

### 7.2 主流程

```text
档案(02) → ICP 向导(引用核心产品/目标市场,可调规则) → 激活
  → 生成查询计划 → 用户确认(plan confirm) → 执行 run
  → 进度/终态(含 PARTIAL/FAILED 如实展示)
  → 线索入队(待人工/已合格/已拒绝)
  → 人工裁决:accept(→ QUALIFIED,发 LeadQualified) / reject(必填原因码)
  → SaaS 事件消费入库 + ACK(资格交付包 GET /leads/:id/package 可下载)
  → 周报导出 → 客户回填反馈 → outcomes 落库
```

### 7.3 功能需求

| 编号 | 功能 | 要求 |
| --- | --- | --- |
| D1 | ICP 向导 | 引用档案的核心产品/目标市场生成初稿;行业/规模/排除条件/买家委员会角色可编辑;激活前可保存草稿;激活走 `POST /icps/:icpId/activate` |
| D2 | 资格规则 | 规则列表增删改(`POST /icps/:icpId/rules`、PATCH/DELETE `/icp-rules/:ruleId`);向用户说明"评分是确定性规则引擎,可复算可审计"(引擎 Lead 模型注释语义);回测(`POST /icps/:icpId/backtests`)展示历史命中 |
| D3 | 查询计划确认制 | `POST /icps/:icpId/query-plans` 生成 → 展示计划要点 → 用户 `POST /query-plans/:planId/confirm` → `POST /query-plans/:planId/execute`;**未经确认不得执行** |
| D4 | run 观察页 | `GET /discovery-runs/:runId` 状态机展示;FAILED/PARTIAL 展示阶段与失败计数,不自动重发(引擎一期 Grant 一次性语义);阶段条、时间预期与失败文案按 §14.3 步骤 4 |

| D6 | 裁决 | accept:可填 reason/reasonCode;**必须处理引擎 409 阻断族**(`SUPPRESSED`、`STORAGE_RIGHTS_NOT_GRANTED`、`SANCTIONS_HOLD_UNRESOLVED`、`SUPPRESSED_CONTACT_UNREACHABLE` 等),转成用户可理解的原因与行动(三层文案规范见 §14.3 步骤 5);reject:**必填原因码**(BI-20,L1–L6 交付循环原因码,#681),界面用选项而非自由文本,原因留痕作质量反馈 |

### 7.4 业务规则

- 一期获客执行的模型/工具成本在引擎侧以执行预算与账本记录;**SaaS 一期不做计费与余额**,执行预算按 Managed 方式由运营在引擎侧配置(已决 SD3);SaaS 事件消费同时按 workspace 留存成本类事件,为二期 billing 归因积累数据。
- 同一 ICP 重复裁决、事件重复投递均幂等处理;以引擎返回与 eventId 为准。
- run 失败不自动重试(引擎 PRD4-D13:验收前 Grant 一次性);界面引导"调整 ICP 后重新生成计划"。

### 7.5 验收标准(节选)

- 从 ICP 激活到看到 lead 入队的完整流程可演示;未确认的计划无法执行。
- accept 后 5 分钟内,SaaS 侧能看到该 `LeadQualified` 事件已入库并 ACK 成功(引擎侧 outbox 相应 delivery 状态变化)。
- reject 无原因码被前端与引擎双重拒绝(422 `REASON_CODE_REQUIRED`)。
- 周报 CSV 下载→回填→outcomes 计数一致。

## 12. 设计决定(2026-10-29 已决)

原八项待决问题由产品负责人委托定案如下,编号 **SD1–SD8**(SaaS 设计决定;与 §7.3 模块 04 的功能编号 D1–D11 是两套序列,互不相干)。每项给出决定、理由与复审条件;复审条件不满足前不得回退。

| 编号 | 问题 | 决定 |
| --- | --- | --- |
| SD1 | 角色集是否加第三档"只读" | **不加**。一期只有 admin/member 两档 |
| SD2 | 一人多工作空间一期是否必做 | **数据模型必做,UI 只做切换器** |
| SD3 | 获客执行预算授予方式 | **2026-10-29 复审后改为 gain-saas 签发**(原“一期 Managed”已废弃);详见 §12 SD3 与 `deploy/engine-integration.md` §4 |
| SD4 | 事件消费 pull+ack 还是 webhook | **pull+ack 为主**,webhook 留作二期双通道 |
| SD5 | `personal-data:read` 授予范围 | **只授事件消费服务身份,永不进用户角色**;SaaS 快照库按含个人数据对待,DSR 级联删除 |
| SD6 | 一期客户准入方式 | **design partner + 邀请码白名单**;注册功能照建但不公开 |
| SD7 | 前端直调引擎 vs BFF 代理 | **BFF 代理**,并立三条铁律(见下) |
| SD8 | 周报反馈五列合同 | **按引擎源码钉死**(见下),不另行定义 |
| SD9 | 获客中台是否独立部署 | **不独立**。并入 gain-saas 运营域,operator 平台角色,三条集成面照搬(见 §13) |

### SD1 角色:两档起步

一期客户是 design partner 小团队(2–5 人),没有真实的只读需求方;"老板只看结果"由 member 已有的 `acquisition:read`(线索列表、周报)覆盖。第三个角色会把 scope 映射的测试矩阵扩大一半,而收益为零。**复审条件**:第一个真实客户明确提出只读/访客需求时,增加 `viewer` 角色(仅 `acquisition:read`),属纯增量变更。

### SD2 多工作空间:模型多对多,UI 最小化

membership 表从第一天就是 `(user_id, workspace_id)` 多对多——这是"改造成本不对称"的典型:现在多对多是零成本,以后从一对一改造要数据迁移 + token 签发流程重构。UI 只做:工作空间切换器 + 创建新空间 + 退出;不做所有权转移、高级空间管理等。引擎侧按 workspace claim 签 token,切换空间 = 换发 token,天然支持。

### SD3 预算:2026-10-29 复审,改为 gain-saas 签发(取代“一期 Managed”)

**原决定**:引擎的 Budget Grant 体系是一次性、短期、请求绑定、reserve/settle;SaaS 一期不做 Billing/Credits,按 Managed 让运营在引擎侧配置,SaaS 不签发 Grant。

**复审原因(实测)**:引擎代码没有“Managed 免 Grant”开关——`verifyWorkspaceGrant` 拿不到 `compactJws` 直接 `EXECUTION_BUDGET_GRANT_REQUIRED`;引擎只验签/消费,签发方由 `EXECUTION_BUDGET_GRANT_ISSUER/JWKS_URI` 单一控制,而原签发方是 GrowthOS(18444),其签发要求 GrowthOS 企业会话并绑定 GrowthOS tenant,无法给 gain-saas 的 workspace 签。结果是建档/ICP/寻源/触达全部 402。

**新决定**:gain-saas 成为 grant 签发方——独立 RSA 钥(与身份钥分离)、`/.well-known/execution-budget-jwks.json`、BFF 先调引擎 quote 再签一次性 Grant;引擎的 `EXECUTION_BUDGET_GRANT_*`(api/worker)改指 gain-saas。`platform-worker` 的副本仍留 GrowthOS(R4 平台 Grant,schedules 仍 paused)。运行合同与 R4 取舍见 `deploy/engine-integration.md` §4。

**保留的约束**:SaaS 事件消费按 workspace 留存成本类事件,为二期 billing 归因积累数据;billing/credits 主账仍在二期。

### SD4 事件消费:pull+ack 主通道

**决定与理由**:pull 是已被引擎验证的合同(GET /events 游标 + POST /events/ack),279 条 PENDING 积压的消除靠的就是确定性回放;一期事件量极小(每周几十条),轮询成本可忽略;pull 不要求引擎到 SaaS 的网络可达、HMAC 密钥管理与推送失败排查——在团队小、合同还在变(#681/#692 刚合)的阶段,把调试复杂度压到最低。

**具体设计**:
- 消费循环:`GET /events?cursor=&limit=&type=` 游标拉取(游标与 ACK 无关、可重放)→ 按 eventId 幂等入库并生成快照 → `POST /events/ack`;ACK 失败只重试 ACK,不重拉。
- 调度:每 2 分钟定时 + 关键动作(lead accept 后)立即触发一次。
- 对账:每日对最近 ACK 的事件抽样调 `GET /events/:eventId/ack-status`(404 不代表未消费,仅 ACKED 可确认)。
- 上线第一步:回放存量 279 条(其中 `LeadQualified` 11 条),作为 G4 的存量验证。
- 抽象:消费侧定义 `EventSource` 接口,pull 是第一个实现;二期启用引擎 webhook sink 时新增 webhook 接收器实现,写同一条幂等入库路径,双通道天然防重。

### SD5 个人数据 scope:唯一服务身份

引擎 `GET /events` 以 AND 语义同时要求 `acquisition:read` 与 `personal-data:read`(守卫逐个校验缺失即 403),因此事件消费服务身份必须持有后者。**这不是红线的让步**:红线从来是"个人数据不进界面、不进用户 token",服务身份两者都不触碰。**必须承接的后果**:SaaS 事件快照库自此属于含个人数据的存储——DSR 删除必须级联(A6 已更新),快照库的访问仅限该服务身份与合规用途,不进任何查询界面。**未来扩张路径**:模块 07 触达需要个人联系点时,同样只授发送服务身份、不进用户角色,且先完成 LIA 与独立合规评审(引擎侧 PRD4-D9 的 LIA 时机仍是未决项,先行确认)。

### SD6 准入:design partner 优先

引擎自助入驻链路故障(§11)、run 0 次全绿、PILOT/GA 治理门死锁——三个现状共同决定一期不能公开自助。注册/邀请功能照常开发(A 组 AC 可完整验收),但入口挂邀请码 + 白名单,规模 2–3 个 design partner,与引擎 RL1 的 PRD4-D8(design partner 人选)对齐,Managed 白手套式入驻。**公开自助的前置条件**(全部满足才开放):引擎入驻修复上线、run 验收全绿、PRD4-D12 流程拍板、SaaS billing 至少有草案。

### SD7 BFF 代理:三条铁律

**决定与理由**:引擎 JWT 只在 SaaS 服务端存在,浏览器仅持 SaaS 会话 Cookie——XSS 偷不到租户 token;引擎合同仍在快速演化(#681/#692/#650 都在一周内合入),BFF 隔离变化;限流、审计、错误归一(409 阻断族 → 用户可读原因)有统一落点。`acquisition-admin` BFF 已验证该模式可行。

**铁律**(违反任何一条即退回):
1. BFF 只做透传、错误映射与审计,不写业务逻辑——防止长出影子 API,与引擎形成双头维护。
2. 引擎 OpenAPI 是唯一合同真值;BFF 不重定义、不"美化"字段,字段含义变化跟着引擎走。
3. run 进度一律轮询(引擎本就是 poll 语义),BFF 不透传长连接/SSE,避免代理层超时与连接管理复杂度。

### SD8 周报反馈五列:按引擎源码钉死

实测引擎 `apps/api/src/report/weekly-report-row.ts` 与 `weekly-feedback.ts`:导出 CSV 共 31 列,其中「线索 ID」为回填 join key,五个「客户填写:」列即反馈合同:

| # | 列名(引擎原文) | 含义 |
| --- | --- | --- |
| 1 | 客户填写:相关性(1-5) | 1–5 整数评分 |
| 2 | 客户填写:愿意联系(是/否) | 布尔 |
| 3 | 客户填写:原因码 | 质量反馈原因(BI-20 语义) |
| 4 | 客户填写:备注 | 自由文本,≤ 2000 字符(`FEEDBACK_MAX_NOTE_CHARS`) |
| 5 | 客户填写:是否已联系(是/否) | 布尔 |

解析规则(引擎已实现,SaaS 不重复实现):分隔符自动识别(`;` 或 `,`)、按「线索 ID」列匹配、空行跳过、坏行带行号拒绝、单文件 ≤ 20000 行(`WEEKLY_FEEDBACK_MAX_RECORDS`)、超限整份拒绝不截断。**反馈路径以在线表格为主**:用户在网页表格里填五列(相关性星级、愿意联系开关、原因码下拉、备注、是否已联系),提交时 SaaS 按本表合同生成 CSV 调用引擎反馈端点——联调时以"同批数据在线提交与原样上传,引擎接受结果一致"做等价性验证;**原样上传 CSV 保留为兜底路径**。SaaS 仍然不做的:解析引擎合同之外的自定义格式、另存一份与引擎语义并行的结构化反馈副本。若引擎后续调整列名,以 OpenAPI 与源码为准更新本表,不在 SaaS 侧做兼容层。

### SD10 双语与主题:一等能力,不是可选装饰

**决定**:一期界面同时支持**简体中文与 English**(launch 即双语,不是后续国际化),并支持**浅色/深色双主题**;登录/注册页与登录后顶栏都保留语言与主题切换。

**理由**:产品的买家侧语境本身是跨语言的——外贸团队日常在中文与英文之间切换,英文界面也是向 design partner 演示与国际团队协作的刚需;深色模式是长时间盯盘(B2B 后台)用户的真实偏好,不能只做浅色再补。

**落地约束**:

1. **文案真值在 `apps/web/src/locales/langs/{zh-CN,en-US}/`**:所有用户可见文案走 i18n key,禁止在组件里硬编码中文或英文;文案包中英键必须完全对齐(可用脚本校验,已纳入开发流程)。
2. **vue-i18n 保留字符**:`@`、`|`、`{ }` 在文案里是语法字符。邮箱示例这类含 `@` 的字面量放在模板属性里,不进文案包(否则整包解析失败、页面白屏)。
3. **设计令牌化**:页面样式一律用 `var(--gs-*)` 语义令牌(`apps/web/src/styles/gainos.css` 定义浅色与 `.dark` 两套),禁止在组件样式里写死颜色;新增颜色先加令牌。
4. **英文排版独立**:拉丁字母的字号、字重、字距与中文不同——英文标题降一档、字距收紧、强调下划线贴基线;以 `.is-en` 作用域承载,禁止中英文共用一套字号导致孤行或挤压。
5. **深色不是反色**:卡片、边框、网格、语义色(警告/危险/品牌绿)在深色下各自取值(品牌绿在深色下提亮以保证对比度),网格与装饰在深色下必须减弱,否则会读成线框稿。
6. **验收**:每个页面在「中文/英文 × 浅色/深色」四种组合下都不出现:文字不可读、装饰压住文案、孤字成行、占位文本截断、切换后布局跳动。

### SD9 中台并入:同服务、独立角色、三条集成面照搬

**决定与理由**:获客中台(acquisition-admin,现以 systemd 独立运行于 4010)是**平台运营视角**——跨租户的 runs/leads/outbox 查看、数据源 Kill Switch、Temporal 调度、预算账户,与租户 admin 是两个信任域。把跨租户能力塞进租户管理员角色会造成越权(租户 A 的 admin 看到租户 B 的数据),所以"直接做进管理员角色"只对一小部分:认领审批、制裁复核、禁联决策这类**租户内**审批功能本就已在 admin 角色(§2.2);其余中台能力归 **operator 平台角色**。但"不再单独弄一个中台服务"完全成立:并入 gain-saas 同一进程、同一登录体系,少一套部署、一套 ADMIN_KEY 与一套独立审计;中台的 ApiKeys 与 external 调试端点直接废弃(分别被 SaaS 账号体系与 SD4 真实消费链路取代)。

**并入规则**:

1. 同一服务三个域:**租户域**(admin/member,业务界面)、**运营域**(operator,§13)、**服务域**(事件消费服务身份、token 签发);登录按账号类型分流,互不可见。
2. 中台对引擎的三条集成面(PostgreSQL 白名单读写、HTTP 健康代理、Temporal)原样照搬,包括 fail-closed schema 探针与写语句白名单登记制——这是中台"零改动引擎"的安全边界,迁移不得丢失。
3. 与 SD7 不冲突:SD7 铁律约束**租户域** BFF 对引擎 HTTP 合同的透传;运营域走的是中台既定的 PG/Temporal 集成面,不新增第四条集成面。引擎未来若补数据源管理 HTTP API,运营域届时迁移。

功能分拣、安全边界与退役步骤见 §13。

## 13. 平台运营域(中台并入,SD9)

面向平台运营(自己人)的运维与排障界面,承接原获客中台(acquisition-admin)的**服务端能力**。运营域不属于九个产品模块,不面向客户,入口与租户域完全分开。运营台**界面不沿用旧中台的 React 页面**——旧界面面向开发者、术语与表格裸奔;按产品负责人决定,新运营台与租户端同栈(Vue 3 + vben),交互按 §14 同等友好标准重写;从中台照搬的是服务端集成资产(白名单注册表、schema 探针、双连接池),不是 UI。

### 13.1 功能分拣(中台 → gain-saas)

| 原中台功能 | 处置 | 一期去向 |
| --- | --- | --- |
| Overview(后端就绪红灯、统计) | 保留 | 运营首页:引擎 `/health/ready`、`/health/build` + PG 统计 |
| Providers(数据源 Kill Switch) | 保留(高危) | PG owner 白名单写照搬;待引擎补管理 API 后迁 HTTP |
| Sources(监控源 CRUD、立即抓取、抓取历史) | 保留 | PG app 白名单写照搬;「立即抓取」仍按"置 `next_fetch_at` 到期 + ACQ_SWEEP 完整管线"语义,不直调采集代码 |
| Schedules(Temporal pause/unpause/trigger/CRUD) | 保留(高危) | Temporal 集成面照搬;trigger/delete/create 二次确认 |

| Export CSV(sources/fetches/entities/leads) | 保留 | 运营导出 |

### 13.2 安全边界(从中台原样继承)

- 两条 PG 连接池:`app_user`(平台表读 + `monitored_source` 白名单写;租户表经 RLS `app.current_workspace_id`)、`owner`(仅两条白名单语句:`data_provider` 启停、`monitored_source` 删除)。
- **写语句白名单登记制**:新增任何写 SQL 必须先登记白名单;schema 探针启动校验表/列,漂移则写端点 fail-closed。
- 运营动作全量审计入 SaaS 审计表;高危操作(Kill Switch、schedule trigger/delete、源删除)二次确认。
- operator 会话不映射任何引擎 scope;运营域与租户域接口互不可调(负向测试见 E1)。

### 13.3 验收标准(E 组)

| 编号 | 验收 |
| --- | --- |
| E1 | operator 登录只见运营域;访问任何租户界面/租户 API 返回 403;admin/member 访问运营域同样被拒 |
| E2 | 数据源 Kill Switch 生效:置 DISABLED 后对应源在新 run 中不再被调用(引擎 `data_provider` 状态回读) |
| E3 | 「立即抓取」触发完整管线(ToolBroker 出网检查、预算、清洗、diff、事件),抓取历史可见;schedule paused 时不抓并有红灯提示 |
| E4 | 白名单写全部落 SaaS 审计;新增未登记写语句被 schema 探针拦截(fail-closed 负向测试) |
| E5 | 中台退役:`acq-admin.service`/`acq-admin-tailnet.socket` 停用后,§13.1 存留项全部可运营 |

### 13.4 迁移与退役

运营域上线并验收 E 组后,一次性切写(gain-saas 运营域接管全部白名单写,中台同时切只读),并行观察一周,然后停用 `acq-admin.service` 与 `acq-admin-tailnet.socket` 并归档。迁移期间避免双头写同一白名单表;中台的 jsonl 历史审计只读保留,不合并改写。

### 14.3 六步主链路体验规范

每步按"呈现 → 动作 → 等待预期 → 出路"四要素定义;出路指失败或异常时用户看到的解释与可做的事。

**步骤 1 完善公司档案**(B1–B3)
- 呈现:分步向导(基本信息 → 核心产品 → 目标市场 → 可选补充),每步可跳过,右侧实时完整度环与"还差什么"清单。
- 动作:必填(公司名、官网、核心产品、目标市场)填完即可提交,其余永远不打断。
- 等待预期:保存即时生效;若触发自动理解,明确"系统正在补充资料,不影响你继续操作"。
- 出路:自动理解不可用时**绝不静默卡死**——"你的填写已保存,系统自动补充暂不可用,可直接手动补全"(B5 兜底)。

**步骤 2 设定目标买家**(D1/D2)
- 呈现:系统按档案预填初稿(行业、市场、排除条件、买家委员会角色),用户**改**而不是从零写。
- 动作:检查 → 激活;资格规则与回测收进「高级」折叠,默认不打扰。
- 等待预期:激活即时。
- 出路:已有生效中的目标买家时,说明"同一时间一个档案跟随一组目标买家",给出去查看/调整的入口。

**步骤 3 确认寻源方案**(D3,确认制的人机界面)
- 呈现:方案要点用人话——"将按以下条件寻找买家":市场与国家、渠道、筛选条件、预计规模;原始查询串折叠在「技术详情」。
- 动作:一个确认按钮,按钮旁写后果:"确认后开始执行,通常 20–60 分钟"。
- 等待预期:确认即执行,无需再点任何东西,自动跳转任务页。
- 出路:方案生成失败 → "换个说法重试"或"联系运营",两选项都可点。

**步骤 4 等待寻源**(D4)
- 呈现:任务页阶段条 `搜索企业 → 收集核实 → 匹配判断 → 补充信号 → 汇总产出`,各阶段完成计数与预计剩余时间区间;**可以离开页面**,完成时站内通知,点击直达结果。
- 等待预期:进入即显示"通常 20–60 分钟,复杂方案更久;完成后通知你,无需等待"。
- 出路:未完成 → 如实展示"本轮找到 X 家后中断"+ 人话原因 + 两个可点选项(调整目标买家重新生成方案 / 联系运营);部分完成 → 突出"已产出 X 条线索,可先去判断",不让中断掩盖已有产出。**绝不自动重发,绝不裸错误码**。

**步骤 5 判断线索**(D5/D6/D8/D9,核心工作面)
- 呈现:队列默认「待我判断」;线索卡片:公司名/国家/**为什么推荐给你**(人话匹配要点,永远首屏)/关键证据链接/五维评分(图标+短句)。个人联系方式不出现(SD5 红线)。
- 动作:每卡片两个主按钮「值得跟进」「暂不跟进」;暂不跟进弹原因**选项**(不自由文本);值得跟进可直接确认。处理后卡片移入对应队列并提示"可在列表找回"。
- 出路:409 阻断按三层文案给行动——禁联 → 解释禁联规则与查看入口;合规待核 → "已通知管理员处理",给管理员直达入口;权利未授予 → 说明含义并留档。制裁复核入口只对管理员露出。
- 辅助:「线索档案包」与「接触草稿」作为详情页内的获取动作,写明"仅用于你自己联系,系统不会代发"。

**步骤 6 周报与反馈**(D10/D11)
- 呈现:本周概览(判断数、跟进数、被拦计数如实);「在线反馈」与「导出 CSV」并排,在线反馈为主路径。
- 动作:反馈表格预填本周线索,逐行点选五列(相关性星级、愿意联系开关、原因码下拉、备注、已联系开关),提交后显示接受/被拒计数,被拒行带原因。
- 出路:整份超限被引擎拒绝时,说明原因并建议分周反馈;兜底「导出后手填再上传」入口保留。

### 14.4 全局交互规范

- **空状态**:核心五页(工作台/公司档案/找买家/买家线索/周报)的空状态必须一句话解释 + **唯一主行动按钮**(如线索页空:"还没有买家线索——去确认一个寻源方案")。
- **加载**:>300ms 出骨架屏;>3s 加进度说明;所有异步按钮有 loading 态防重复提交。
- **错误三层**:发生了什么 / 为什么 / 怎么办;「技术详情」折叠区保留错误码与 trace id,一键复制(供运营排障),默认收起。
- **通知中心**:统一站内通知(铃铛 + 未读角标):寻源任务终态、认领审批结果、合规待核解除、反馈处理结果;每条通知点击直达对应详情。一期不做邮件/短信。
- **不可逆操作**:确认弹层写明后果与不可撤销(暂不跟进、认领审批、禁联、方案确认);系统侧终态动作不提供假撤销。
- **文案规则**:全中文、业务动词(「确认方案」不是「execute plan」);数字带单位;时间标注时区;计数与 withheld 如实展示;一处概念一个词(本 PRD 与界面共用 §14.2 词表,不再同义混用)。
- **行内解释**:可达性("为什么显示'联系不上'")、证据来源、评分维度等概念配「?」行内解释,解释文案集中维护,术语与 §14.2 一致。
- **页面焦点**:一页一个主按钮;次要操作收进「更多」;高级能力(规则、回测、禁联明细)不挡主链路。
